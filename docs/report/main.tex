\section{Deployment overview}

One small HTTP service runs in two environments; this report records how each manages it. Everything sits in four layers (Figure~\ref{fig:topology}). The physical host is a Windows 11 workstation running VMware Workstation 17.6.1. Inside it, a virtual machine named \code{cs554-vm} runs Ubuntu Server 24.04.5 with 2 vCPUs, 4 GiB of RAM, and a 25 GiB disk, attached to VMware's NAT network \code{192.168.197.0/24}; the host owns \code{.1} on that network and the VM received \code{.134} from VMware's DHCP \evid{00-host-vm.md}{VM facts}. Inside the VM, Docker Engine 29.1.3 runs the containers. For Part~2, Docker Compose 2.40.3 runs the service container directly. For Part~3, a k3d 5.9.0 cluster runs a single k3s 1.37.1 node as a Docker container on the same engine, and the Kubernetes Pods run inside that node container. At the bottom of every path is the same process: Node 22 running the course starter's \code{server.js}, which answers \code{GET /} with a JSON body (service name, message, hostname, and a request counter kept in process memory) and \code{GET /health} with HTTP 200.

Both environments use one container image, built once inside the VM from \code{app/Dockerfile}. Compose runs it from the local Docker image store; the cluster receives it through \code{k3d image import}, and the Deployment sets \code{imagePullPolicy: Never} so the cluster can only use the imported image \evid{02-kubernetes.md}{Import the same application image}. No registry is involved. The image was first built as \code{cs554-midterm:1.0}; the CS~554 readiness experiment added a four-line toggle to \code{/health} and rebuilt it as \code{1.1}, which both environments now run. Earlier captures showing \code{1.0} are unchanged.

\section{Docker Compose inside the VM}

The Compose file declares one service, \code{web}, built from \code{../app} and configured through environment variables (\code{PORT}, \code{SERVICE\_NAME}, \code{MESSAGE}) read from an uncommitted \code{.env} file whose defaults are committed as \code{.env.example}, with VM port 8080 published to the container's port 8080 and a health check calling \code{/health} every ten seconds \evid{01-compose.md}{Resolved Compose configuration}. The health check deliberately targets \code{/health}, which the service does not count, so it never disturbs the request counter.

From inside the VM, three requests to \code{GET /} returned counts 1, 2, and 3 from the container hostname \code{864d1c1b9d87}, and \code{/health} returned HTTP 200 \evid{01-compose.md}{VM requests and health}. From the Windows host, \code{curl.exe http://192.168.197.134:8080/} returned count 4 from the same container \evid{01-compose.md}{Windows host request}. The host reaches the VM directly on its NAT address; VMware's NAT device routes between the host adapter and the guest, so no port forwarding was configured. \code{docker compose ps} showed the container \code{Up (healthy)}, and the logs showed the startup line \code{Listening on port 8080} followed by one JSON line per request, including the periodic \code{/health} probes \evid{01-compose.md}{Startup and request logs}.

The restart experiment is the observation the rest of the report leans on. With the count at 5, \code{docker compose restart} stopped and started the container: the logs recorded \code{Received SIGTERM; stopping.} and then a fresh \code{Listening on port 8080}, and the next request returned count 1 \evid{01-compose.md}{Restart and counter reset}. The container kept its name and hostname; only the process inside it was new, and the counter lived in that process. Throughout, the health check's own requests appear in the logs as \code{/health} lines and never moved the counter. \code{docker compose down} removed the container and its network; the service was then brought back up for the walkthrough \evid{01-compose.md}{Cleanup demonstration}.

\section{Kubernetes}

The cluster runs inside the same VM: k3d creates the node as a Docker container from the image \code{rancher/k3s:v1.37.1-k3s1}, pinned so that the server matches the installed kubectl 1.37.1 \evid{02-kubernetes.md}{Create the cluster}. A Deployment named \code{cs554-midterm} asks for two replicas of the image, labels its Pods \code{app=cs554-midterm}, and a ClusterIP Service of the same name selects that label and maps port 80 to the container's named port \code{http} (8080). After \code{kubectl apply}, the Deployment reported \code{2/2}, both Pods were \code{1/1 Running}, and the Service's EndpointSlice listed two endpoints \evid{02-kubernetes.md}{Apply and two ready replicas}.

Requests went through the Service in two ways, because they demonstrate different things. From a client Pod inside the cluster, six requests to \code{http://cs554-midterm/} by DNS name were answered by both Pods, each with its own counter; this shows the Service resolving to ready backends across replicas, though not round-robin ordering or fairness \evid{02-kubernetes.md}{In-cluster Service requests}. A \code{kubectl port-forward svc/cs554-midterm 18080:80} session inside the VM answered three requests all from one Pod: port-forward uses the Service's selector only to choose a Pod, then tunnels to that Pod through the API server, so it proves reachability but says nothing about traffic distribution \evid{02-kubernetes.md}{VM-local Service port-forward}.

Deleting one Pod showed what distinguishes Kubernetes from Compose. With Pods \code{mkspb} and \code{ndjs4} running, \code{kubectl delete pod} on \code{mkspb} was followed within three seconds by a new Pod, \code{2jmll}, in \code{ContainerCreating}, which was \code{Running} at three seconds and \code{1/1} ready at six; the ReplicaSet returned to desired/current/ready 2 and logged a \code{SuccessfulCreate} event \evid{02-kubernetes.md}{Automatic Pod replacement}. Kubernetes replaced the Pod because the ReplicaSet controller continuously reconciles the Pods it observes against the Deployment's declared \code{replicas: 2}; one Pod short, it created another, without any further command. The replacement's first request counted 1 \evid{02-kubernetes.md}{Replacement process counter}. The comparison with Part~2 is direct: Compose restarted the same container's process because an operator told it to, whereas Kubernetes created a different Pod, with a new name, on its own. Both lost the in-memory counter, because in both cases the process was new; what differed was who decided and what identity survived.

\section{Controlled troubleshooting: the Service selector}

A Service is a label query, and the EndpointSlice is the result of that query. The experiment changed one line in \code{service.yaml}, the selector from \code{app: cs554-midterm} to \code{app: cs554-midterm-typo}, and applied it; nothing else changed \evid{03-selector-break.md}{Exact selector change}. From the client Pod, three requests to the Service by DNS name failed with \code{curl: (7) Failed to connect to cs554-midterm port 80 ... Could not connect to server}, exit code 7. A port-forward session started fresh after the change exited with \code{error: timed out waiting for the condition}, and its request also failed with exit 7 \evid{03-selector-break.md}{In-cluster client symptoms; Fresh port-forward failure}. The session had to be fresh: an old port-forward would have stayed pinned to the Pod it chose earlier and hidden the fault.

The observations separate the cause from everything it was not. Both Pods stayed \code{1/1 Running} with zero restarts and their labels unchanged; the Deployment's UID, generation, and spec were byte-identical before, during, and after; the Service's selector read \code{app=cs554-midterm-typo}; the EndpointSlice had no endpoints (kubectl 1.37 renders an empty endpoint set as \code{<unset>} and a blank \code{Endpoints:} line, where older versions printed \code{<none>}); and the Pods' logs from the moment of the change onward contained only readiness probes and not one \code{GET /} \evid{03-selector-break.md}{Failure diagnosis}. The cause follows: no Pod carried the label the selector asked for, so the EndpointSlice controller computed an empty backend set, kube-proxy had no destination for Service traffic, and port-forward could not pick a Pod. Re-applying the correct \code{service.yaml} restored two endpoints, and both client paths succeeded again, with the same Pod names and zero restarts throughout \evid{03-selector-break.md}{Correct selector and recovery}.

Recovery has a timing subtlety of its own. The EndpointSlice is recomputed as soon as the selector matches again, but the node's forwarding rules are rewritten by kube-proxy's own control loop, which keeps them synchronized with the API state \cite{k8s-virtual-ips}, so for an instant after the object lists both backends a request can still be refused. The README's recovery step therefore retries the request and records the attempt on which it succeeded: a successful request, not a populated EndpointSlice, is the evidence that the Service is back.

Healthy Pods therefore prove nothing about reachability through a Service. Readiness is a statement about a process: it can serve. A Service's endpoints are a statement about a match: these Pods carry the labels this selector names. The two are evaluated independently, and either can be true while the other is false. A diagnosis that stops at \code{kubectl get pods} sees two healthy replicas and no problem; it must also compare the selector to the labels, inspect the EndpointSlice, and test a client path that depends on the match.

\begin{enumerate}
\item \textbf{The resource settings and why}: requests \code{cpu: 50m}, \code{memory: 64Mi}; limits \code{cpu: 250m}, \code{memory: 128Mi} (QoS class \code{Burstable}, because requests differ from limits). Facts: the service is one Node process; the VM showed 505~MiB used in total with it running; two replicas on a 2-vCPU node; the limits leave burst headroom without letting one replica starve the other.
\item \textbf{Distinguish a request from a limit}: a request is what the scheduler reserves on a node to place the Pod; a limit is the ceiling enforced at run time (CPU above the limit is throttled; memory above the limit gets the container killed).
\item \textbf{How readiness affects Service traffic, and how it differs from restarting a container}: the readiness probe governs whether the Pod is a ready endpoint of the Service; it does not restart anything. Facts from the experiment (evidence/04-readiness-554.md): after the toggle, Pod A was \code{0/1 Running} with \code{RESTARTS 0}; its EndpointSlice entry went \code{ready: false}; all ten in-cluster requests went to Pod B; A still answered a direct request and its counter continued 4~$\rightarrow$~5~$\rightarrow$~6 across failure and recovery. A liveness failure or a restart would have produced a new process and a reset counter, which did not happen.
\item \textbf{Why this method}: a running Pod's readiness probe is immutable, so a per-Pod probe patch is not possible; the documented application-level toggle (\code{READINESS\_FILE}) was the handout's permitted alternative. The Deployment template changed only in the rollout before the baseline; the experiment itself touched one file in one Pod and restored it.
\end{enumerate}}
