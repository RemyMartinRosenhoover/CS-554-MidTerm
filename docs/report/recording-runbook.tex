\section{Purpose and scope}

This is the procedure I follow to record the four-minute walkthrough, and it is written so that a reader can reproduce the demonstration on an environment built from the README. Each step gives the command I enter, the result I expect, and the check I make before moving on. The expected results are the outputs I observed when I rehearsed this procedure on 19 October 2026 against the running environment; they are shown unedited apart from trimming one over-long line.

The guide assumes the environment the README describes, built and deployed as far as Part~3: the VM is running, the Compose service is up on port 8080, and the k3d cluster holds the two-replica Deployment, its Service, and the client Pod. It demonstrates what Parts~2--4 of the README establish; it does not repeat the CS~554 readiness experiment, which is documented in the README's CS~554 section and in \code{evidence/04-readiness-554.md}.

\paragraph{Conventions.} Commands marked \emph{VM} are entered in an SSH session inside \code{cs554-vm}; commands marked \emph{host} are entered in Windows PowerShell on the machine that runs VMware. Blocks are pasted as shown, without prompt characters. Some values are live and will differ from the rehearsal; I read them from the screen rather than from this page:

\begin{center}\small
\begin{tabular}{@{}ll@{}}
\toprule
Live value & Where it appears \\
\midrule
Guest address (\code{192.168.197.x}) & step 2, host request; found in precondition P1 \\
Pod names (\code{cs554-midterm-<hash>-<id>}) & steps 3--5 \\
Ages, request counters & every output; counters rise by one per request \\
Recovery attempt number & step 5, \code{recovered on attempt N} \\
\bottomrule
\end{tabular}
\end{center}

\paragraph{Windows.} The README open in a browser (steps 1 and 6); \emph{Terminal~1}, an SSH session at \code{\textasciitilde/CS-554-MidTerm/compose}; \emph{Terminal~2}, an SSH session at \code{\textasciitilde/CS-554-MidTerm}; one host PowerShell window. Only P1, P6, and the host request in step~2 run on the host; every other block runs inside the VM. Each SSH session is opened from its own PowerShell window with the README's connection line:
\begin{verbatim}
$work = Join-Path $env:USERPROFILE 'cs554-work'
$keys = Join-Path $work 'keys'
$key = Join-Path $keys 'cs554_vm'
$knownHosts = Join-Path $keys 'known_hosts'
$ip = Get-Content -LiteralPath (Join-Path $work 'logs\cs554-vm-ip.txt')
ssh -i $key -o "UserKnownHostsFile=$knownHosts" "student@$ip"
\end{verbatim}

\section{Preconditions}

I run these checks in order and do not start until all seven pass. A failure is corrected with the restoration steps in Section~4, after which the checks are run again from P1.

\paragraph{P1 --- The VM is running and has an address} (host).
\begin{verbatim}
$vmrun = "${env:ProgramFiles(x86)}\VMware\VMware Workstation\vmrun.exe"
& $vmrun -T ws list
& $vmrun -T ws getGuestIPAddress C:\VMs\cs554-vm\cs554-vm.vmx
\end{verbatim}
Expected: the list names \code{C:\textbackslash VMs\textbackslash cs554-vm\textbackslash cs554-vm.vmx}, and the address is on \code{192.168.197.0/24}. I note the address; step 2 uses it.

\paragraph{P2 --- The checkout is at the current \code{main}} (VM).
\begin{verbatim}
cd ~/CS-554-MidTerm
git status --porcelain
git fetch -q origin && git rev-parse --short HEAD origin/main
\end{verbatim}
Expected: \code{git status} prints nothing, and the two hashes are identical. If they differ, \code{git pull --ff-only origin main} and repeat.

\paragraph{P3 --- The Compose service is healthy} (VM).
\begin{verbatim}
docker inspect -f '{{.State.Health.Status}}' compose-web-1
curl -s localhost:8080/health
\end{verbatim}
Expected: \code{healthy}, then \code{\{"status":"ok"\}}.

\paragraph{P4 --- The cluster is at its baseline} (VM).
\begin{verbatim}
kubectl get deploy cs554-midterm
kubectl get pods -l app=cs554-midterm
kubectl get pod client
kubectl get svc cs554-midterm -o jsonpath='{.spec.selector.app}'; echo
kubectl get endpointslices -l kubernetes.io/service-name=cs554-midterm -o json \
  | jq '[.items[].endpoints[]? | select(.conditions.ready == true)] | length'
for p in $(kubectl get pods -l app=cs554-midterm -o name); do
    kubectl exec "$p" -- test -f /tmp/ready && echo "$p readiness file present"
done
\end{verbatim}
Expected: Deployment \code{2/2}; two application Pods \code{1/1 Running} with \code{RESTARTS 0}; \code{client} \code{Running}; selector \code{cs554-midterm} (not \code{cs554-midterm-typo}); ready endpoints \code{2}; both Pods report the readiness file.

\paragraph{P5 --- No forwarder is left over} (VM).
\begin{verbatim}
pgrep -af 'kubectl.*port[-]forward' || echo "no forwarder"
ss -ltn '( sport = :18080 )'
\end{verbatim}
Expected: \code{no forwarder}, and the \code{ss} table contains only its header line.

\paragraph{P6 --- The host reaches the service} (host, with the address from P1).
\begin{verbatim}
curl.exe -i http://<address>:8080/health
\end{verbatim}
Expected: \code{HTTP/1.1 200 OK} with body \code{\{"status":"ok"\}}.

\paragraph{P7 --- The recording setup is ready.} The four windows are arranged inside the capture region with a readable font; nothing personal is visible (no taskbar, notifications, other tabs, or host paths); a five-second test clip has been recorded and played back with audible audio.

\section{Procedure}

Timings are the on-camera budget: 20, 50, 50, 40, 60, and 20 seconds, four minutes in total.

\subsection*{Step 1 --- Opening (0:00--0:20)}

\subsection*{Step 5 --- Troubleshooting finding (2:40--3:40)}
Purpose: break the Service selector, show healthy Pods with no endpoints, restore it, and show recovery measured by a successful request. The restore block is the README's ``Restore and verify'' block, unchanged.

\enter{VM, Terminal 2; failure group}
\begin{verbatim}
kubectl apply -f k8s/service-broken.yaml
kubectl get svc cs554-midterm -o jsonpath='{.spec.selector.app}'; echo
for attempt in $(seq 1 20); do
    count=$(kubectl get endpointslices -l kubernetes.io/service-name=cs554-midterm -o json \
      | jq '[.items[].endpoints[]? | select(.conditions.ready == true)] | length')
    if test "$count" -eq 0; then break; fi
    sleep 1
done
test "$count" -eq 0
failure_exit=0
kubectl exec client -- curl -sS --max-time 5 http://cs554-midterm/ || failure_exit=$?
printf 'Expected failed request exit: %s\n' "$failure_exit"
test "$failure_exit" -eq 7
kubectl get pods
kubectl get endpointslices -l kubernetes.io/service-name=cs554-midterm
\end{verbatim}
\observed
\begin{verbatim}

cs554-midterm-typo

command terminated with exit code 7
Expected failed request exit: 7

client                           1/1     Running   0          24h
cs554-midterm-67c66d7b5d-2v5mx   1/1     Running   0          114m
cs554-midterm-67c66d7b5d-l2ffr   1/1     Running   0          21h
NAME                  ADDRESSTYPE   PORTS     ENDPOINTS   AGE
cs554-midterm-q55pw   IPv4          <unset>   <unset>     24h
\end{verbatim}

\enter{VM, Terminal 2; restore group}
\begin{verbatim}
kubectl apply -f k8s/service.yaml
for attempt in $(seq 1 20); do
    count=$(kubectl get endpointslices -l kubernetes.io/service-name=cs554-midterm -o json \
      | jq '[.items[].endpoints[]? | select(.conditions.ready == true)] | length')
    if test "$count" -eq 2; then break; fi
    sleep 1
done
test "$count" -eq 2 || { echo 'Two ready endpoints did not return'; exit 1; }
kubectl get svc cs554-midterm -o jsonpath='{.spec.selector}'
kubectl get endpointslices -l kubernetes.io/service-name=cs554-midterm -o wide
kubectl describe svc cs554-midterm | grep -E 'Selector|Endpoints'
recovered=
for attempt in $(seq 1 20); do
    if kubectl exec client -- curl -sS --max-time 5 http://cs554-midterm/; then recovered=$attempt; break; fi
    sleep 1
done
echo "recovered on attempt ${recovered:-none}"
kubectl get pods -l app=cs554-midterm --show-labels
\end{verbatim}
\observed
\begin{verbatim}
service/cs554-midterm configured
{"app":"cs554-midterm"}
NAME                  ADDRESSTYPE   PORTS   ENDPOINTS               AGE
cs554-midterm-q55pw   IPv4          8080    10.42.0.17,10.42.0.19   24h
Selector:                 app=cs554-midterm
Endpoints:                10.42.0.17:8080,10.42.0.19:8080
curl: (7) Failed to connect to cs554-midterm port 80 after 0 ms: Could not connect to server
command terminated with exit code 7
{"service":"cs554-k8s","message":"Hello from Kubernetes inside the VM","hostname":"cs554-midterm-67c66d7b5d-l2ffr","requestCount":50}
recovered on attempt 2
NAME                             READY   STATUS    RESTARTS   AGE    LABELS
cs554-midterm-67c66d7b5d-2v5mx   1/1     Running   0          114m   app=cs554-midterm,pod-template-hash=67c66d7b5d,tier=web
cs554-midterm-67c66d7b5d-l2ffr   1/1     Running   0          21h    app=cs554-midterm,pod-template-hash=67c66d7b5d,tier=web
\end{verbatim}
In this rehearsal the EndpointSlice already listed both backends when the first request was made, and that request was still refused; the second succeeded. That is the behavior the retry exists for: the EndpointSlice is updated before the node's forwarding rules are, so a successful request, not a populated EndpointSlice, is the evidence of recovery.
\talk{Healthy Pods alone do not prove the Service works. Its selector is a label query, and the typo leaves it with no matching endpoints, so the request is refused while both Pods are running. After the correction the endpoints return at once, but the node's forwarding rules follow a moment later; the request is retried until it succeeds, here on attempt N.}
\checkpoint{the JSON response and \code{recovered on attempt N} are on screen with a number, and both Pods carry \code{app=cs554-midterm}.}
\stoprule{if the line reads \code{recovered on attempt none}, I stop the recording, keep the output, and run the restoration in Section~4; I do not claim recovery on camera.}

\section{Restoration and verification}
\cmdblock

\subsection*{Restore after every run, finished or abandoned}
\begin{verbatim}
cd ~/CS-554-MidTerm
kubectl apply -f k8s/service.yaml
kubectl rollout status deploy/cs554-midterm --timeout=120s
pkill -f 'kubectl.*port[-]forward' || true
\end{verbatim}
Expected: \code{service/cs554-midterm unchanged} (or \code{configured}, if a run was abandoned during step~5), \code{successfully rolled out}, and no error from \code{pkill}.

\subsection*{Verify the baseline}
Preconditions P3, P4, and P5 are run again and must pass exactly as before: a healthy Compose service; \code{2/2}; two Pods \code{1/1} with zero restarts; selector \code{cs554-midterm}; two ready endpoints; both readiness files; no forwarder. The Pod names differ from before step~4; that is expected.

\subsection*{Reset for another run (optional)}
Nothing has to be reset: counters continue from where they are, and the talking points read the values on screen. If fresh counters are wanted, the following restarts the processes without changing a manifest or the Deployment:
\begin{verbatim}
cd ~/CS-554-MidTerm/compose && docker compose restart && cd ..
docker compose -f compose/compose.yaml ps
kubectl delete pod -l app=cs554-midterm
kubectl rollout status deploy/cs554-midterm --timeout=120s
\end{verbatim}
Expected: Compose back to \code{Up \ldots\ (healthy)} with its next request counting \code{1}; two new application Pods \code{1/1} with new names and empty counters. The full set of preconditions is run again before recording.

\subsection*{Completion criteria}
The demonstration is complete when the recording shows all six steps with their expected results, the restoration has been run, the baseline has been verified, and the recording plays back with legible output and audible commentary. Compose, the cluster, and both replicas stay running afterwards.

\section*{Appendix: recording notes}

I record with Camtasia: a capture region that holds the terminals and the browser, microphone on, 1080p, exported as MP4. Every window stays inside that region. If Camtasia is unavailable, Snipping Tool's screen recorder is the second option and PowerPoint's Record Screen the third. The recording is uploaded unlisted, the link is opened in a private browser window to confirm it plays without a sign-in, and the link is then added to the README and the submission note.
